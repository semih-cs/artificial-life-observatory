## 1. Canonical Phase 0A tick / same-tick resolution semantics

**Previous open issue.** §20.11 stated that the exact same-tick resolution order "remains subject to implementation validation," and at least four sections (§12.16 food competition, §12.32-area feeding/reproduction/death precedence, §15.4, §18.12 RNG consumption order) either restated this as open or left it implicit. In particular it was unresolved whether an organism that would die from movement/metabolic cost in a given tick could still feed and then reproduce in that same tick.

**Selected design.** A single normative 20-phase tick order was written (new §20.72): Snapshot → Sense → Decide → Movement resolution → Movement energy cost → Feeding / food competition → Energy gain → Reproduction eligibility check → Reproduction resolution → Parent cost → Child creation (mutation + placement) → Death resolution → Apply births/removals → Food regeneration → Telemetry → Advance tick. Food competition among organisms contesting the same food item is resolved deterministically by distance-to-food with organism-ID as an explicit tie-breaker (not by any organism/birth-order-derived quantity, to avoid structural bias). Birth resolution consumes RNG in parent-ID order, with mutation and placement draws sequenced deterministically after that ordering, and food-regeneration RNG draws are sequenced after births/removals are applied. A normative `stepWorld()` TypeScript-style pseudocode function implementing this exact phase order was included. The feeding-rescue question is answered explicitly: because feeding and energy gain occur before death resolution in the phase order, an organism that would otherwise die from movement cost in this tick can be rescued by feeding in the same tick, and — because reproduction eligibility/resolution also occurs before death resolution — it can also reproduce in that same tick, provided it independently satisfies reproduction eligibility after the energy gain.

**Classification.** `[LOCKED]` — this changes deterministic event meaning and experimental interpretation (which organisms live, reproduce, or die in a given tick), not merely an implementation convenience.

**Affected sections.** New §20.72 (authoritative). Cross-referenced from: §12.16, §12.32-area (Decision Summary items), §15.4 (Phase 0A Implementation Contract, rewritten from an `[OPEN]` restatement to a resolved cross-reference), §18.12, and the RESOLVED-tagged paragraphs at every prior occurrence of the same-tick-conflict question throughout §12, §15, §20, and the Decision Summary/Final Open Questions material.

**Remaining empirical variables.** None specific to tick order itself. The magnitude of any distance/food-competition-adjacent numeric parameters (e.g., feeding range, movement cost coefficients) remains `[OPEN — EMPIRICAL]` as before and was not touched.

## 2. Final Phase 0A sensory input vector

**Previous open issue.** The sensory schema was scattered and partially open: whether the input vector should be nearest-food vs. sector-based, whether wall-sensing needed its own representation, whether organism age should be exposed, and whether reproductive readiness should be directly exposed or inferred, were each separately `[OPEN]`, with no single coupled resolution and no per-input normative definition (index, meaning, normalization, frame of reference, phenotype dependency, edge-case behavior).

**Selected design.** A single six-input normative schema was written (new §11.58), with indices 0–5 each carrying exactly one, non-overlapping physical meaning: `input[0]` = foodVisible (binary presence flag, gated by visionRange/visionAngle), `input[1]` = foodDistance (normalized by visionRange, in (0, 1], 0 when no food visible), `input[2]` = foodAngle (signed organism-relative bearing to the nearest visible food, normalized to (-1, 1]), `input[3]` = boundaryDistance (normalized by half the world's shorter dimension, phenotype-independent baseline sense, always defined), `input[4]` = boundaryAngle (signed relative bearing to the nearest boundary point), `input[5]` = normalizedEnergy (energy / energyCapacity, clamped to [0, 1] — the single physiological input; there is no second or duplicate energy-related index). Every input's coordinate frame, normalization divisor, and edge-case behavior (no food visible, zero distance, exact boundary contact, corner ties) is defined per-input, with a shared angle/sign convention across all bearing inputs. The representation is nearest-visible-food only — there is no sector-based visual field for Phase 0A, which makes the previously-open visionAngle/sector-resolution question moot rather than answered. Organism age is not exposed as an input. Reproductive readiness is not directly exposed; it is inferred by the network only insofar as normalizedEnergy correlates with it, consistent with keeping the primitive internal-state boundary intact.

**Post-review correction (Revision 4).** The version of this report accompanying Revision 3 paraphrased this schema imprecisely — describing indices 4 and 5 as "wallProximity" and separately "energyLevel" *and* "normalizedEnergy," which read as a duplicate physiological input. On review of the authoritative §11.58 text (verified programmatically: the string "energyLevel" does not occur anywhere in the specification), the schema was already correct and unambiguous as written above — six unique indices, one energy input. §11.58 was given one added clarifying sentence stating this explicitly, and two stale example-list references to "exact/final neural input dimensionality" elsewhere in the document (predating §11.58, never updated) were retired. No redesign was needed or performed. See the Revision 4 addendum at the end of this report.

**Classification.** `[LOCKED]` — the sensory contract fixes what information is available to evolution and is directly an experimental-interpretation and architecture-invariant question (changing it later changes what strategies are evolvable), not a calibration value.

**Affected sections.** New §11.58 (authoritative). Cross-referenced from §11.6–§11.17 (perception requirements it satisfies), §15.2 (Phase 0A Implementation Contract's Perception bullet), and RESOLVED-tagged paragraphs replacing the prior scattered `[OPEN]` items on sector representation, wall-sensing, age exposure, and reproduction-readiness exposure.

**Remaining empirical variables.** None. This was a coupled architectural decision, not a calibration one; no numeric constants (e.g., vision range magnitude) were finalized here — those stay `[OPEN — EMPIRICAL]` where they already were.

## 3. Neural activation and output semantics

**Previous open issue.** The hidden-layer activation function and the per-output activation/decoding rule for all four outputs (forward, turn, eat, reproduce) were `[OPEN]`, and it was unclear whether the eat/reproduce action thresholds needed to be finalized as part of closing this area.

**Selected design.** A single normative activation/output specification was written (new §11.59): hidden layer uses `tanh`; forward output uses `sigmoid` mapped to `[0, 1]` (fraction of max move speed, phenotype-scaled); turn output uses `tanh` mapped to `[-1, 1]` (signed fraction of max turn rate, phenotype-scaled); eat and reproduce outputs use `sigmoid` in `[0, 1]`, compared against a threshold using a `>=` comparator (the action fires when output is greater than or equal to the threshold). The comparator itself (`>=` rather than `>`) is fixed because it is a determinism question — it affects exact-tie behavior identically for every organism and every run given the same seed, not a calibration magnitude. The numeric threshold values (`eatThreshold`, `reproductionActionThreshold`) are explicitly NOT finalized in this pass, per instruction; a placeholder note states that a provisional `[BASELINE]` test-fixture value may be used for early unit tests but must not be presented as validated or final.

**Classification.** Hidden/output activation function choice and the `>=` comparator: `[LOCKED]` (deterministic event meaning — identical behavior at exact ties is required for reproducible cross-run comparison). The numeric action-threshold values: remain `[OPEN — EMPIRICAL]`, unchanged and explicitly untouched.

**Affected sections.** New §11.59 (authoritative). Cross-referenced from §11 (neural controller description), §15.2, and the RESOLVED-tagged paragraph replacing the former `[OPEN]` "exact action thresholds" block, which now reads as comparator-resolved / value-still-open.

**Remaining empirical variables.** `eatThreshold`, `reproductionActionThreshold`, and any reproduction-energy threshold magnitude — all explicitly `[OPEN — EMPIRICAL]`, unchanged from before this pass.

## 4. Founder Neural Genome generation method and deterministic bootstrap construction

**Previous open issue.** §13.27 (Founder Neural Genome) and §13.29 (Bootstrap Population) each independently marked their generation/selection method as `[OPEN]`, with no concrete, deterministic procedure connecting "one common Founder Neural Genome" to "a bootstrap population of related initial neural genomes via small perturbations."

**Selected design.** A single normative four-step procedure was written (new §13.76): (1) draw the Founder Neural Genome's weights/biases from BootstrapRNG using a fixed, documented distribution; (2) apply a mechanical-validity check only (correct shapes, no NaN/Inf, no structural corruption) — never a fitness or behavior check; (3) apply a minimal viability screening step against a small precommitted fixed synthetic probe set, checking five binary pass/fail conditions: non-degeneracy (non-constant output — rules out a dead/saturated network), movement is mechanically possible, food is approachable under the sensor/action model (turn output moves heading toward, not away from, visible food), eating is mechanically possible, and reproduction is mechanically possible under a fixed diagnostic probe — never a fitness ranking, comparison, or trajectory simulation between candidates; (4) on rejection, retry by continuing to draw from the same BootstrapRNG stream (no restart, no reseeding, no branching search). The procedure explicitly enumerates what is forbidden: no searching among multiple candidate genomes to pick the "best" one, no trajectory or fitness preview of any candidate, no hand-authored/hand-tuned weights standing in for a sampled genome. The bootstrap population is then built by drawing small, fixed-distribution perturbations of the Founder genome (continuing BootstrapRNG), one per bootstrap organism, preserving common ancestry exactly as already specified (this was not reopened). Bootstrap-population placement uses a `placeWithMinSeparation()` helper to avoid degenerate spatial overlap; the minimum-separation distance itself is `[BASELINE]`, not empirically validated.

**Post-review correction (Revision 4).** This report's original description of step 3 undersold what the authoritative §13.76 text already allowed: it read as if only NaN/Inf and output-saturation checks were permitted, narrower than the "minimal functional smoke checks" the base specification intends. §13.76 was expanded from three named checks to the five above (adding food-approachability and reproduction-possibility, which were previously implicit/missing), all still strictly binary pass/fail against a fixed, precommitted probe set, with no ranking, scoring, or cross-candidate comparison introduced. See the Revision 4 addendum at the end of this report.

**Classification.** The four-step procedure and its allowed/forbidden boundary (mechanical validity + minimal viability screening allowed; adaptive optimization/search forbidden): `[LOCKED]` — this is a core research-philosophy invariant (no hand-engineered starting sophistication, no optimization pre-seeding evolution) and changes experimental interpretation if altered later. The minimum-separation distance value: `[BASELINE]`.

**Affected sections.** New §13.76 (authoritative). Cross-referenced from §13.27, §13.29, §15.6, and RESOLVED-tagged paragraphs replacing the prior `[OPEN]` founder-generation-method items and the offspring-placement/newborn-heading and minimum-separation items (which are handled in the same normative pass since they share the deterministic-construction mechanism).

**Remaining empirical variables.** Founder/bootstrap perturbation sigma magnitude remains `[OPEN — EMPIRICAL]`, unchanged and explicitly on the do-not-resolve list.

## 5. Concrete Phase 0A PRNG / RNG stream implementation

**Previous open issue.** §18.8–§18.18 established the requirement for isolated RNG streams (BootstrapRNG, CanonicalRNG) and purpose-based seed derivation, but named no concrete algorithm, seeding function, or Gaussian sampling method, leaving the PRNG algorithm, the seed-derivation/hash function, and the sub-stream granularity all `[OPEN]`.

**Selected design.** A single normative implementation spec was written (new §18.70): xoshiro128** is named as the concrete generator (chosen and justified as a fast, well-distributed, non-cryptographic, 32-bit-friendly PRNG suitable for JS/TS numeric environments — explicitly not cryptographic, since none is needed). `next()`, `nextFloat()` (uniform `[0,1)`), and `nextInRange()` semantics are defined precisely. Gaussian sampling uses the Box-Muller transform over two `nextFloat()` draws. Per-purpose stream seeding is defined as `streamSeed(purpose) = splitmix32(rootSeed XOR PURPOSE_CONSTANT[purpose])`, with splitmix32 used only for deterministic state-expansion/seeding of each xoshiro128** stream, not as the running generator itself. A `PURPOSE_CONSTANT` table is defined with `bootstrap` and `canonical` as the two active Phase 0A streams and `analytics`, `probeSampling`, `probeExecution` reserved (named but unused) for later phases. The two-stream minimum (Bootstrap + Canonical) is locked as sufficient for Phase 0A; finer fragmentation (separate FoodRNG/MutationRNG/OffspringPlacementRNG/ConflictResolutionRNG sub-streams) is explicitly deferred rather than adopted now, to avoid unnecessary stream fragmentation, and is to be introduced later only if a demonstrated need appears.

**Classification.** `[LOCKED]` — the *requirement* that canonical randomness be deterministic, stream-isolated, dependency-injected, and versioned. The decision to defer finer stream granularity and the two-stream minimum: `[LOCKED]` as a Phase 0A scope boundary (not a value to calibrate).

**Post-review correction (Revision 4).** This report originally classified the concrete algorithm, seed-expansion scheme, and Gaussian method themselves as `[LOCKED]`. On review this was too strong: an implementation choice that determines trajectory reproducibility for a given seed is not the same kind of thing as a research-methodology or biological-semantics invariant — it can legitimately be replaced later, provided the replacement is an explicit `simulationVersion` bump so old seeds are never silently reinterpreted. §18.70's concrete xoshiro128** algorithm (now with fully explicit bit-level step/rotation and unsigned-32-bit arithmetic semantics), the splitmix32 seed-expansion scheme (now with an explicit all-zero-state prohibition), and the Box–Muller Gaussian method (now closing the `ln(0)` edge case via a fixed one-draw `nextFloatOpen01()` mapping rather than a retry loop) are reclassified `[BASELINE — VERSIONED]` — a sub-tag of `[BASELINE]`, newly defined in §5.3, for exactly this shape of decision. The underlying RNG *contract* (isolation, determinism, versioning, no `Math.random()` in canonical code, serializable state) remains `[LOCKED]` and was not touched. See the Revision 4 addendum at the end of this report.

**Affected sections.** New §18.70 (authoritative). Cross-referenced from §18.8–§18.18, §15.5 (Determinism Contract), and RESOLVED-tagged paragraphs replacing the prior `[OPEN]` PRNG-algorithm and seed-derivation items. The two genuinely-distinct prior `[OPEN]` strings for "final seed-derivation/hash algorithm" (one `[OPEN]`-prefixed, one not) were both individually located and resolved to avoid silently merging non-identical paragraphs.

**Remaining empirical variables.** None — this is a fully deterministic implementation decision with no calibration-dependent magnitude.

## Revision 4 addendum — three final specification hotfixes

Applied after final review, before implementation began. No other design topic was reopened; no specification rewrite was performed.

**Hotfix 1 — sensory schema dimensionality (§11.58, §5.3).** On review, §11.58's authoritative text already defined six unique, non-overlapping inputs with exactly one normalized-energy input — verified programmatically (the string "energyLevel" does not occur anywhere in the document). The apparent duplicate energy input existed only in this report's own imprecise paraphrase (now corrected above, §2). §11.58 was given one added sentence explicitly closing the doubt ("there is no second or duplicate energy-related input at any other index"). Two stale example-list bullets elsewhere ("exact/final neural input dimensionality," predating §11.58) were retired and replaced with a genuinely-open example (neural bootstrap perturbation sigma). Classification: unchanged, `[LOCKED]` (§11.58 itself was not redesigned, only clarified).

**Hotfix 2 — PRNG classification and Box–Muller edge case (§18.70, new §5.3 sub-tag).** The concrete xoshiro128** algorithm, splitmix32 seed-expansion, and Box–Muller Gaussian method are reclassified from `[LOCKED]` to `[BASELINE — VERSIONED]` — a new sub-tag defined in §5.3, meaning: concrete and implementable today, but replaceable later only under an explicit `simulationVersion` bump, since changing it changes what a given seed reproduces. The underlying RNG contract (isolation, determinism, no `Math.random()`, serializable state, versioned consumption order) remains `[LOCKED]`, unchanged. xoshiro128**'s state initialization is now fully explicit: a bit-precise `rotl`/`next()` implementation with unsigned-32-bit arithmetic semantics (`>>> 0` / `Math.imul`), an explicit prohibition on the all-zero state with a defined fallback, and a precise `nextFloat()` definition. The Box–Muller `ln(0)` edge case is closed by a new `nextFloatOpen01()` — a fixed one-draw mapping, `(next() + 0.5) / 2^32`, strictly excluding both 0 and 1 for every possible generator output — used for the first Box–Muller draw; no retry loop or unpredictable draw count is introduced. Gaussian sampling is documented as consuming exactly two draws per result, with the paired value deterministically discarded rather than cached, per the "simpler deterministic state model" preference.

**Hotfix 3 — founder minimal-viability screening (§13.76).** Expanded from three checks (non-degeneracy, minimal movement, minimal eating) to the originally-intended five: non-degeneracy, movement possible, food approachable under the sensor/action model (turn output moves heading toward visible food), eating possible, and reproduction possible under a fixed diagnostic probe. All five remain strictly binary pass/fail against one precommitted, fixed synthetic probe set defined before any candidate is drawn — no ranking, no scoring, no comparison between candidates, no trajectory simulation, and no selection of "the best" candidate were introduced. Classification: the five-check protocol itself is `[LOCKED]` (part of the founder-generation/screening procedure); the probe-set fixture values remain `[BASELINE]`.

**Verification performed after all three hotfixes:**
1. Section numbering — top-level sections remain sequential 1–26 with no gaps or duplicates (programmatically re-verified).
2. Neural input dimensionality — confirmed unambiguous everywhere: zero occurrences of "energyLevel," zero remaining stale "exact/final neural input dimensionality" references, §11.58's clarifying sentence present.
3. `[LOCKED]` principles — none reopened. The two reclassifications (PRNG concrete implementation, founder-screening detail level) moved items *into* more accurate tags (`[BASELINE — VERSIONED]`, expanded `[LOCKED]` protocol detail); no existing `[LOCKED]` biological-semantics, architecture, or research-philosophy principle was weakened, removed, or contradicted.
4. Empirical values — unchanged. No action-threshold, sigma, energy-coefficient, or other `[OPEN — EMPIRICAL]` value was finalized in this pass; all remain exactly as listed above.
5. New blockers — none created. All three hotfixes were closures/clarifications of existing normative text, not new open design questions.
